The shared payment popup now has a compact one-line product/price summary, a smaller title and spacing, sourced payment artwork, and distinct CARD/NAVER/TOSS/KAKAO POST choices. It remains explicitly labelled as a payment-window connection test with no real payment. Owned-credit spending remains unavailable because it is not wired to the production ledger; it is not redirected to the mock-credit page as a substitute.

Official reference: https://developers.nicepay.co.kr/docs/pg/auth/payment-window-skip/ . NAVER uses E020 and E020=CARD, TOSS uses E025 and E025=CARD, KAKAO uses E016; all use CARD and DirectShowOpt=CARD. Browser-supplied method names are allowlisted and cannot supply arbitrary protocol fields. Prices/MID/signature remain server-controlled. A direct-window diagnostic first displays the official NICE terms/privacy links and requires the user's own acknowledgement before its SDK launch button becomes available. No consent is preselected, accepted by the agent, or represented as a stored commercial purchase consent record.

The public review callback still does not submit authentication for approval. All return/approve/cancel/fulfill requests remain 409 without an approval transport or database. A selected brand is a diagnostic request, not evidence the merchant supports that method. NICE may reject it based on merchant enablement. No real brand-window launch, user authentication, payment approval, or credit spend is claimed by the automated tests. Those browser/merchant checks remain pending because the Whale control binding is failing. Do not activate these parameters in real payment processing without verified merchant authority and the production consent/storage design.

## Inline consent and click guidance

The payment selector now prepares an initially unchecked, single-line required-consent control with expandable individual notices, synchronized all/partial selection, keyboard focus and a status message. Attempting a payment without consent prevents native form submission, highlights the consent row and briefly shakes it when reduced-motion is not requested. It never checks consent on behalf of the user. This UI-only change does not add a new SDK launch or approval path.

Automatic approval review initially rejected no-intermediate-page SDK launch because it did not recognize sufficiently specific amount/method authorization. Those rejected patches were not applied or worked around. The user subsequently explicitly confirmed: KRW 9,900/seven authentication windows may be launched directly while real approval stays blocked. The authorized image-only path now requests JSON diagnostic fields after the three notices are checked, verifies the test-only marker, MID, exact amount and blocked return URL, and calls the official SDK in the existing page. Other unpriced products cannot use this direct path. Native form navigation is prevented; callbacks never submit authentication for approval. Merchant support and real browser/device behavior still require verification.

Nine tests pass, covering consent/version requirements, all seven JSON method configurations, forged amounts, rejection of unpriced products, animation/focus before consent, reduced motion, same-page SDK invocation, blocked approvals and cancellation when the selector is closed before the response. Consent is user-selected and ephemeral in this diagnostic UI; it is not a durable commercial consent receipt or an enabled production transaction. An actual successful approval, provider execution, credit grant, refund or completed merchant review must not be inferred from this rollout.
