# 충전형 크레딧 개발 및 활성화

## 확정 정책

- 1크레딧 = 1,000원. 10개 10,000원 / 50개 50,000원 / 300개 300,000원.
- 모든 묶음 할인 0%. 보너스 크레딧이나 결제 쿠폰을 적용하지 않는다.
- 고객 사유의 충전 환불은 `max(0, 충전 실결제액 - 사용 크레딧 × 구매 당시 정상 단가)`로 예상액을 계산한다. 현재 정상 단가는 개당 1,000원이다. 미래 할인 상품도 이 기준으로 정산하며 추가 청구는 없다. 법령상 환불 권리·사업자 귀책 사유는 별도 검토가 우선한다.
- 기존 개별구매를 유지하며, 지원 도구의 결제 시 개별구매/크레딧을 선택한다.
- 크레딧 차감은 정수 올림. 예: 단건 4,500원 → 5크레딧.
- 고객 이메일은 로그인 링크로 검증한다. 지갑 잔액, 원장, 주문, 로그인 토큰 해시는 비공개 SQLite에 영구 저장한다.
- `src/pages/credits.astro`가 `/credits/` 화면이다. 기본은 준비 중이며 돈을 받지 않는다.

## 차감량과 원가

`CREDITS_TOOL_PRICING_JSON`에 상품별 검증된 원화 판매가와 변동 원가를 넣는다.
USD 상품을 실시간 환율 추측으로 자동 변환하지 않는다. 현재 사이트의 여러 단건 상품은 USD이므로, 운영자가 원화 기준 판매가를 정해야 한다.

```json
{
  "ai_personal_color": { "retailKrw": 4500, "costKrw": 1000, "feeBps": 1000, "marginBps": 2000 }
}
```

위 숫자는 사용자 설명을 재현한 **계산 예시이며 실제 퍼스널컬러 원가가 아니다**. 환경변수 기본값은 `{}`다.

```
최소 판매액 = ceil(변동원가 / (1 - 수수료율 - 목표마진율))
차감 크레딧 = ceil(max(단건 원화 판매가, 최소 판매액) / 1000)
```

수수료율 기본 10%, 목표마진율 기본 20%는 보수적 설정값이며 실제 Polar 수수료를 의미하지 않는다. 원가에는 재시도·모델·호스팅 등 변동 비용을 포함한다. 고정 결제 수수료는 가장 작은 10개 팩 기준으로 수수료율에 반영한다. 원가가 오르면 값을 갱신해야 하며 코드가 실제 원가를 자동 관측하지는 않는다. 목표마진율은 최소 10% 이상, 수수료와 합해서 100% 미만이어야 한다.

현재 연결 상품 키:

| 키 | 적용 상품 |
| --- | --- |
| `base` | 증명사진·여권사진·AI 포토샵·AI 이미지 생성의 기본 구매 |
| `video_mkv_mp4` | MP4 변환 1건 |
| `ai_name_premium` | 동일 입력에 대한 이름 분석·추천 묶음 |
| `ai_pet_translator` | 결제일로부터 30일 이용권 |
| `calorie` | AI 칼로리 분석 |
| `ai_personal_color` | AI 퍼스널컬러 |
| `ai_manseryeok` | AI 만세력 |
| `detail_page_5`, `_7`, `_10`, `_15`, `_20` | 상세페이지 장수별 결과 |

원가 미입력 상품 및 별도 사진 추가 생성 옵션(`add2/add3/add7` 등)은 기존 개별구매를 유지한다. 추가 옵션은 기존 API에 독립적인 소모/복구 경로가 없어 크레딧 허용 목록에 포함하지 않았다. 기부는 크레딧 대상이 아니다. `base`는 기존 사이트에서 사진과 이미지 생성이 공유하므로 두 경로 중 높은 원가를 적용한다. 펫 원가는 1회 호출이 아닌 30일 이용권 전체에 대한 비용 상한을 넣어야 한다.

## 서버 및 결제 설정

1. 크레딧 기능은 `node:sqlite`를 지원하는 Node 22.13 이상(Node 24 권장)이 필요하다. 기능을 끈 기존 API는 기존 Node 조건을 유지한다.
2. 영구 디스크에 `CREDITS_DB_PATH`를 지정한다. 기본 위치는 `node-api/private-credit-data/wallets.sqlite`이며 git 제외다. `/files`로 공개되는 `node-api-storage` 하위 경로는 시작 시 거부한다. 파일·상위 폴더 권한은 서비스 계정으로 제한하고 SQLite 백업 API 또는 안전한 DB 백업 절차로 백업한다. WAL 파일을 무시한 DB 단독 복사를 하지 않는다.
3. 기존 서버 한 인스턴스와 로컬 영구 볼륨으로 운영한다. SQLite 원장 트랜잭션은 다중 연결 차감을 보호하지만 기존 생성 작업은 메모리에 있어 서버 여러 대로 분산 운영하는 구성은 지원하지 않는다.
4. Polar에 고정가·일회성 KRW 상품 3개를 준비한다. 10,000원/50,000원/300,000원 상품 ID를 `POLAR_PRODUCT_CREDITS_10/50/300`에 넣는다. 체크아웃 전에 API로 상품의 통화·가격·정기결제 여부를 검증한다. 체크아웃 통화도 KRW로 고정하며 할인 코드 입력을 금지한다.
5. `/credits/webhook`으로 `order.paid`, `order.refunded` 이벤트를 연결한다. `POLAR_WEBHOOK_SECRET` 표준 서명이 필수다. 기존 `/payment/webhook`의 임시 토큰 fallback은 크레딧에서 사용하지 않는다.
6. `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `PUBLIC_WEB_BASE_URL`을 설정한다. 브라우저 Origin과 웹 주소가 정확하게 같아야 한다. API는 웹과 같은 사이트의 서브도메인에서 HTTPS로 제공한다. 세션은 HttpOnly/Secure/SameSite=Lax 쿠키이며 브라우저 저장소에 인증 토큰을 저장하지 않는다.
7. `CREDITS_TOOL_PRICING_JSON`을 실제 원가로 설정하고 지원 AI 도구가 정상 작동하는지 확인한다. 현재 `Layout.astro`의 AI 준비 중 차단은 유지했다. 해당 유지보수 종료와 연동해서 `CREDITS_TOOLS_READY=true`로 바꿔야 한다. 프론트 차단 중에는 크레딧 선택도 우회되지 않는다.
8. 샌드박스 결제·서명 웹훅·결과 생성·실패 복구·환불을 확인한 뒤 `CREDITS_ENABLED=true`, 프론트 `PUBLIC_CREDITS_ENABLED=true`로 활성화한다. 실제 API 키나 결제 상품은 이 개발 작업에서 생성/변경하지 않았다.

기능을 다시 끌 때 `CREDITS_DB_PATH`는 유지한다. 이 경로가 있으면 새 충전/차감은 꺼도 로그인·원장 조회·미사용 취소·환불 접수 및 환불 웹훅을 처리한다. 로그인 이메일 발송 설정도 유지한다.

## 중복·실패 처리

- 결제 이벤트의 실제 상품 ID, 체크아웃 ID, 통화, 세전 결제액, 할인액, paid 상태를 검증한다. 이벤트 중복/재시작으로 재충전하지 않는다.
- 크레딧 사용 요청은 이메일+요청 키로 멱등 처리한다. 차감과 주문 생성은 한 트랜잭션이다. 클라이언트의 `amount`/`credits`를 사용하지 않는다.
- 실행 시작은 DB에서 원자적으로 선점한다. 동시에 같은 주문으로 실행해도 한 요청만 진행한다.
- 확인된 실패는 한 번만 복구한다. 음식이 아닌 칼로리 사진도 복구한다. 상세페이지 결과는 성공했고 이메일만 실패한 경우는 중복 환급하지 않는다.
- 비동기 이미지·영상은 큐 접수 시 성공 처리하지 않고 작업 완료/실패 시 원장을 확정한다. 이름 프리미엄은 최초 성공 후 동일 입력에 대한 기존 분석·추천 이용 범위를 유지한다. 펫은 결제 시 30일 이용권이 발급되므로 미사용 취소 대상이 아니며, 개별 호출 실패가 이용권 전체 자동 환급으로 이어지지 않는다.
- 입력 검증 또는 API 미설정으로 실행 전에 멈춘 주문은 지갑에서 미사용 취소가 가능하다.
- 생성 중 서버가 강제 종료되면 성공 여부가 불명확하므로 자동 재실행/자동 환급하지 않는다. 운영자가 `purchases.state='processing'` 주문과 공급자/결과 로그를 확인한 후 처리한다. 임의로 SQL 잔액을 수정하지 말고 `CreditStore.finish(id, false)`를 사용해 복구 원장을 남긴다.
- 충전별 사용량은 FIFO로 배분한다. 취소·실패 복구는 원래 충전으로 반환된다. 환불 예상액 조회는 남은 잔액을 잠그지 않으며, 실제 접수 시 최신 사용량과 예상액이 일치하는지 트랜잭션 안에서 다시 확인한다.
- 접수 시 해당 충전의 미사용 크레딧을 모두 잠그고 원장에 기록한다. 진행 중/미사용 주문이 있으면 완료 또는 취소가 먼저 필요하다. 접수 재시도는 같은 접수번호를 반환한다. 구매 당시 조건은 `topup_terms`에 저장하며, 조건/배분 내역이 없는 이전 충전·사용은 자동 정산하지 않는다.
- 사이트 환불 요청과 일치하는 Polar 환불 알림은 이미 잠근 잔액을 다시 차감하지 않고 완료 처리한다. 예: 300개/290,000원 중 5개 사용 → 285,000원 환불, 남은 295개 전부 회수. 요청액과 다른 환불 알림은 `review`로 전환하고 추가 구매를 중단해 수동 대조한다.
- 사이트에서 접수하지 않은 결제사 직접 환불은 기존 비례 회수 흐름으로 처리한다. 이미 썼으면 음수 잔액이 되어 추가 구매를 차단한다. 결제보다 환불 알림이 먼저 와도 뒤늦게 크레딧을 다시 지급하지 않는다.
- 적립금 양도·출금·쿠폰·보너스·자동충전·자동갱신은 구현하지 않았다. 충전 환불은 기존 고객지원 및 Polar 관리 흐름을 사용한다.

## 환불 접수 운영

`POST /credits/refund/quote`는 인증된 본인의 `topupId`에 대한 예상액을 반환한다. `POST /credits/refund/request`는 `topupId`, `usedCredits`, `refundAmount`, `policyVersion`, `confirmed:true`를 받아 서버에서 다시 계산하고 접수한다. 클라이언트 금액을 정산 원본으로 사용하지 않는다.

접수만으로 카드 취소를 실행하지 않는다. 운영자는 비공개 DB의 `refund_requests` 중 `requested` 상태를 확인하고, `topups.provider_order`의 Polar 주문에서 접수된 금액을 환불한다. 세금은 결제사 처리 기준을 따른다. 서명된 `order.refunded` 웹훅을 수신해야 완료된다. `review`는 결제사 실제 누적 환불액과 고객 권리를 대조한 후 수동 조정해야 하며 임의 SQL로 잠금을 해제하지 않는다. 법정 환불이나 사업자 귀책 사유가 있으면 정상가 공제 문구만으로 거절하지 않는다.

신규 충전은 환불정책 버전 확인값이 있어야 체크아웃을 생성한다. 할인 상품 판매 자체는 여전히 비활성이다. 할인 도입 시 팩의 가격 변경뿐 아니라 최소 실수령 단가에 맞춘 원가 하한 검토가 필요하다.

테스트는 외부 유료 API나 실제 결제를 호출하지 않는다. 가격 올림·원가 하한, 재시작, 중복 지급/차감, 잔액 부족, 실행 선점, 실패 복구, 취소 권한, 부분/전체/역순 환불, 로그인 만료/일회성, Origin, 서버 가격 검증 및 결제상품 불일치를 다룬다.
