## Category-specific preparation (follow-up)

`nicepay-policy.js` separates `credit_topup` from `direct` approvals. Empty configuration is disabled. Even explicit `enabled` and `apiConfirmed` only permit **offline intent preparation**, not real payment. `requireNicepayLive()` still rejects unconditionally. Existing Polar routes remain unchanged; do not automatically redirect a rejected NICE transaction to Polar.

The policy is parsed from trusted server configuration with `readNicepayPolicy(raw)`. Each category independently requires `approved`, a `methods` array containing `card`, and an explicit positive `maxAmountKrw`. Current implementation supports only one-time domestic KRW card payment. Recurring, overseas, billing, easy-payment and mobile methods are rejected, including for direct products, until a separately reviewed implementation exists. The cap is a merchant-side safety limit, not a substitute for each card issuer's daily/monthly limits.

`prepareNicepayIntent(request, catalog, policy)` looks up price, currency, quantity, category and label from a **trusted server catalog**. Never construct that catalog or ownerId from unauthenticated request data. The caller must supply the authenticated verified account and the server-owned product configuration. Browser-supplied prices/categories/credits are ignored. This change does not create a new live catalog or alter existing prices. Direct payment labels are now supported by the request builder. ASCII labels are enforced while the selected form encoding remains untested.

Before routing public checkout, persist the returned intent with a random order ID, expiry and authenticated owner. Validate against that immutable persisted record during authentication/approval/ledger settlement. This module intentionally does not treat provider policy approval as an authorization to charge, expose a checkout, or credit an account.


## NICE PG transport (NPG documentation confirmed)

The provider documentation links NPG and identifies the MID/MerchantKey/goPay contract as the integration target. Per-MID eligibility, test keys and card review remain unverified. `nicepay-pg.js` now implements the matching ASCII/EUC-KR-compatible test form, signed authorization HTTP request, bounded UTF-8 JSON response validation and explicit signed network cancellation. Network transport defaults disabled. Unit tests explicitly enable a mocked fetcher; no NICE endpoint was called.

`server.js` mounts `/payments/nicepay/config` (enabled=false), `/payments/nicepay/checkout` and `/payments/nicepay/return` (503). No environment switch opens these endpoints. Existing Polar is untouched. The form renderer is not served publicly and does not auto-open a payment window.

Approval timeouts, HTTP errors, invalid signatures/amounts and malformed responses produce `NICEPAY_UNCERTAIN`. Approval is never retried automatically. Network cancel is explicit and validates the matching DC destination, signature and amount. It is not a general refund API. Caller must persist uncertain/cancelled outcomes and reconcile; a validated response alone does not grant a balance.

Still required before staging checkout: durable random order/owner/expiry binding; atomic lock and unique transaction ID; crash recovery/reconciliation; bounded UTF-8 callback parser; authenticated server catalog; fulfillment and rollback/refund ledger; rate limits and CSP; merchant test keys; browser/mobile tests. The current client is therefore not wired to an incoming callback or account credit. Source for network cancel: https://developers.nicepay.co.kr/docs/pg/auth/net-cancel/ .

## Durable orders and reconciliation preparation

`nicepay-orders.js` adds a separate private SQLite store (Node with `node:sqlite` required). It is not initialized by the running server and the disabled public routes are unchanged. The caller must select a persistent path outside `/files`, restrict permissions and configure SQLite-aware backups before staging use.

- Order creation snapshots the trusted server intent, authenticated owner and merchant MID, with a random ID and 15-minute authentication expiry.
- A transaction claims `created -> approving` and a unique TID before sending approval. Concurrent/repeated callbacks and TID reuse are rejected before network I/O.
- Verified provider receipts are persisted once with the transition to `verified`. This state means a payment receipt has been validated, **not that wallet credits or a tool entitlement have been delivered**.
- Timeout/failure after the network attempt enters `uncertain`; approval is not replayed. `recoverStale` moves interrupted `approving` records to the reconciliation queue after at least 60 seconds.
- `reconcilePgApproval` verifies a signed matching PG response against the saved MID/order/amount/TID before resolving an uncertain record. It does not make a status-query or approval request. Provider status-query transport and operational scheduling remain to be built/verified.
- Keys, callback auth tokens and full provider responses are not stored. Therefore a restarted process cannot automatically perform auth-token network cancellation; reconciliation/status query is required. Do not claim automatic cancellation after restart is complete.

Offline tests now cover reopen/restart, duplicate/concurrent callbacks, transaction-ID collision rollback, owner access, expired orders, wrong MID, timeout ambiguity and signed reconciliation. Still needed: atomic wallet/direct-entitlement fulfillment with durable outbox, ordinary refund/cancellation state integration, provider status query, secure callback parsing and real merchant sandbox tests. Never expose `recordVerified` as an HTTP endpoint or accept its input directly from a browser.

## Staging callback and shared-wallet fulfillment

`nicepay-callback.js` now supplies an **unmounted, disabled-by-default staging router**. It supports authenticated same-origin product checkout, the PG form renderer and a bounded URL-encoded return endpoint. Enabling it requires explicit dependencies, the confirmed legacy policy, an HTTPS origin, and order/wallet stores in the same persistent SQLite file. Mount this router before any broad body parser. The current `server.js` still mounts only the disabled routes. No environment variable activates staging automatically.

The authentication adapter must return the verified email used by the existing credit wallet. Supabase project or user IDs are not assumed to be wallet identities. No Supabase configuration was changed. For a future Supabase adapter, verify project/audience/token server-side and establish a reviewed account mapping first.

`nicepay-fulfillment.js` uses the verified receipt plus immutable saved intent. A transaction creates a NICE-specific topup lot, shared-wallet ledger change and fulfillment marker together; repeat processing is a no-op. A crash after receipt storage leaves a recoverable pending-fulfillment query. The receipt and fulfillment transactions are intentionally distinct: receipt evidence survives a fulfillment failure. Pending fulfillment must be replayed operationally before launch.

Direct purchases create a separate owner/product-bound one-use entitlement. Claiming is atomic; **actual tool execution, interrupted-job recovery and refund restoration are not yet wired to these entitlements**. Do not enable direct checkout until this integration is complete.

Existing Polar and Play behavior remains. NICE lots are shown with provider `nicepay`. Polar webhooks cannot mutate them and the Polar refund route explicitly rejects them. This prevents charging/refunding through the wrong processor, but ordinary NICE refunds are still an unresolved release blocker, not an unsupported user right. Keep checkout disabled until NICE refund operations and recovery are implemented.

The offline HTTP integration test uses a fictional authenticated user and mocked PG transport: checkout -> signed callback -> receipt -> shared wallet, plus origin rejection, callback replay and malformed input. No live NICE or AI calls were made. Remaining release blockers include real MID test keys/eligibility, browser/mobile flow, status-query transport and scheduler, ordinary refunds, direct tool execution integration, request rate limits, CSP and operational review, full production catalog approval and deploy authorization.

## Execution, inquiry and cancellation follow-up

- `nicepay-execution.js` adds durable direct-tool job claims, saved bounded result references, idempotent result retrieval and limited pre-execution failure recovery. Only a trusted adapter proving `executionNotStarted=true` restores the entitlement (maximum two attempts). Timeout, crash or uncertain tool completion does not re-run automatically. The staging `/execute` route authenticates the owner, derives the product from its saved order, and calls a server-only adapter registry after validation. **No existing paid AI tool adapter is registered in production**, and all public NICE routes remain disabled.
- The PG client now implements documented transaction inquiry and full-card cancellation, disabled by default. Fixed official endpoints only; no arbitrary URL, automatic refund or retry. Full cancellation verifies amount, cancel order ID, signature and zero remainder. Partial cancellation is not implemented. Wallet reservation/debit, durable refund locking/reconciliation and customer refund flow still require integration before checkout can open.
- Transaction inquiry returns only TID/status, not amount/order/signature. An `approved` status is therefore explicitly marked `fulfillmentAllowed=false`; it cannot by itself grant credits. Resolving lost approval receipts still needs sufficient provider evidence or cancellation handling.
- Review corrections: topup amount must equal credits × 1,000 before checkout and again before approval; refund version/unit price are frozen in the order snapshot; matching verified callback replay can finish pending fulfillment without a second approval; `recoverNicepayFulfillments` provides an explicit local pending-payment replay runner; authentication adapters may be asynchronous. Refund consent presentation/capture remains a launch requirement.

Official operation references: https://developers.nicepay.co.kr/docs/pg/auth/payment-cancel/ and https://developers.nicepay.co.kr/docs/pg/inquiry/trans-inquiry/ . General reconciliation services may require provider-enabled MID access and IP registration; no access settings were changed.

## Unused full-refund reservation and actual tool adapter

`nicepay-refund.js` now reserves **fully unused full refunds only**: credit balance is held and the lot becomes unavailable in the same transaction, or an unused direct entitlement is locked. Active/used credit allocations reject full refunds. A reservation can be released only before dispatch. Dispatch is persisted before the request; timeout/crash keeps the hold and enters an explicit reconciliation queue without automatic retry or automatic restoration. A signed matching full-cancel response finalizes the held refund exactly once. Partial/used-credit refunds, exceptions, automatic query resolution, customer refund UI and operational scheduling remain incomplete; do not enable public checkout yet. No refund endpoint is exposed.

`nicepay-tool-adapters.js` supplies an opt-in adapter for the existing `commerce/sajuAnalyzer.js#analyzeSaju` implementation, with awaited input validation and bounded supported fields. Default registry is empty. Tests inject a fake analyzer and incur no AI calls. The production server registers no adapter. Real outputs, artifact storage/size, AI failure UX and browser execution require staging validation before enabling this adapter. Existing product prices are unchanged.

Refund withdrawal review fix: each new reservation now generates its own cancellation ID and hold/release ledger keys. A released reservation is rechecked for current unused balance/entitlement eligibility before renewal, then archived transactionally. Repeated withdrawal/reservation cannot reuse a previous ledger debit or credit. Tests cover repeated cycles followed by cancellation and spending between withdrawal and a later request.

## Customer-form staging (separate default-off gate)

`customerEnabled: true` explicitly enables `/customer/` inside the still-unmounted server assembly. Without it the customer route returns 503, even when diagnostic staging is enabled. This is a wallet-authenticated, non-operator flow for the registered saju, calorie, personal-color and detail-page products. Existing production Astro pages/Polar checkout are untouched: their old order polling and fulfillment IDs must not receive a NICE ID as a drop-in replacement.

The customer page has normal date/time, image upload, meal-goal, notes and product-description forms, displays only configured catalog prices, validates input before order creation, opens the PG form explicitly, checks verified entitlement readiness and runs the purchased analysis. Results are safely rendered as text sections, not HTML supplied by an AI. There is no raw JSON input requirement. Customer checkout uses a durable owner/request-key mapping and normalized input hash: simultaneous retries reuse one order, altered input cannot reuse that request, and repeated execution uses its cached result. Payment input bodies are not stored in this mapping, only hashes. The client keeps the request key in sessionStorage, not the birth date/photos; a reload requires re-entering the same input to recover the existing order. Expired/uncertain orders are not silently replaced with another charge. A separate explicit “new analysis” action appears only after completion.

Offline HTTP regression covers the non-operator real-cookie flow through normal form delivery, validation, double-submit, signed fake approval, entitlement, immutable execution input, result replay and other-owner rejection. It does not run an actual browser or external PG/AI. Client-side file limits match the existing bounded adapters. Human-friendly localization of provider-specific report keys, detail-page HTML/export rendering and full browser accessibility/mobile validation remain UI work. Photo/image, pet/name and video have authenticated backend/diagnostic flows but do not yet have corresponding consumer forms in this new route. No complete all-tools consumer-UI claim is made.

Review correction: normalized customer input binding is now enforced in the shared execution coordinator before either a fresh claim or cached-result replay, including generic payment routes. Calls without a validated input cannot execute a customer-bound order. Client validation failures explicitly marked as pre-order safe reopen the form and rebuild its input while preserving the request key.
