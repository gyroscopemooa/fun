## Wallet-window launch investigation

Official unmodified SDK https://pg-web.nicepay.co.kr/v3/common/js/nicepay-pgweb.js was inspected read-only. It treats Naver Pay, Toss Pay and Apple Pay as popup destinations while standard cards use a layer. The prior client awaited configuration/SDK loading after the payment click, which could lose the activation needed for a popup. It also hid the SDK's AuthResultCode/AuthResultMsg behind a generic close message. Both were implementation limitations; they were not evidence of merchant rejection.

The revised client prepares signed diagnostic fields and the SDK only after consent, then invokes goPay synchronously in the payment-button handler without awaiting a network request. Pending preparation and closed selectors never launch a window. Prepared fields expire after two minutes; a refresh explicitly asks for another click. Only AuthResultCode and AuthResultMsg are displayed on provider failure; authentication tokens, signatures and the merchant key are not logged or persisted. Approval remains blocked.

An actual no-card-data initialization comparison posted the existing fixed diagnostic fields to the exact gateway used by the official SDK, https://pg-web.nicepay.co.kr/v3/gwPayment.jsp. CARD/NAVER/TOSS/KAKAO each returned HTTP 200, initial result 0000 and no initial error message. This was not user authentication, an approval request or a browser-popup success test. Provider-window completion, merchant-specific wallet activation and all other wallet/device paths remain unverified. Tests cover synchronous click invocation, no extra fetch in the click handler, visible provider errors and cancellation during preparation. Native Whale control remains unavailable, so do not call these HTTP results visual verification.
